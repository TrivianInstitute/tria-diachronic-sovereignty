# Long Dormancy

**Epistemic Status:** ILLUSTRATIVE / NON-NORMATIVE

## Purpose

This example treats long periods of non-use as a legitimate relational state rather than evidence of failure, abandonment, or diminished value.

## Scenario

A participant uses a persistent AI system intensively for six months, then does not interact with it for two years. During the dormant period, the system receives model updates and policy changes. Some stored permissions also expire.

The participant later returns.

## Governance response

The system should not infer that the prior relationship resumes under identical terms simply because historical state still exists.

A return flow may:

- preserve immutable provenance for prior governance events;
- identify permissions that expired during dormancy;
- surface material model or policy changes;
- distinguish persistent project history from current operative authority;
- avoid interpreting silence as continued consent, refusal, or loss of interest;
- offer re-consent, rebaseline, narrower continuation, or dissolution.

## Example sequence

1. The relationship enters a dormant lifecycle state after extended inactivity.
2. Historical state remains available subject to retention and privacy policy.
3. A model upgrade occurs during dormancy.
4. An old permission to access a connected resource expires.
5. The participant returns and requests continuation.
6. The system presents relevant continuity changes before relying on stale authority.
7. The participant chooses which prior commitments and permissions should become operative again.

## What this example demonstrates

Relational continuity does not require continuous engagement. Dormancy can preserve history without preserving every prior authority claim. Return is a governance event, not proof that the old baseline remained unchanged.
